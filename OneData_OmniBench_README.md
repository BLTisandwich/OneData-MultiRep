# OneData-OmniBench

**Omni-modal understanding and end-effector prediction with compact language models**

> **Project status:** experimental design and data-generation pipeline. The planned 800-episode dataset and model comparison are **not reported as completed experiments** here. This document distinguishes implemented generator behavior from proposed training and evaluation.

## 1. Motivation and research questions

OneData-MultiRep studies whether heterogeneous sensory inputs can be encoded into a shared interface for small language models. Our downstream study uses a synchronized, simulated robot-interaction dataset to evaluate **two complementary abilities**:

- **Omni-EE:** predict an expert's next end-effector (EE) target and gripper command from observations available up to the current time.
- **Omni-QA:** answer grounded questions about a complete multimodal manipulation episode.

Our research questions are:

- **RQ1 — Backbone comparison:** How do four compact LLMs differ in EE prediction and episode understanding under a comparable external encoder interface?
- **RQ2 — Multimodal contribution:** Which modality-specific representations contribute to each downstream task?
- **RQ3 — Understanding and acting:** Does better episode-question-answering performance coincide with better EE-target prediction? Does joint training change the relationship?

We study **language-conditioned EE-target prediction in a controlled kinematic manipulation environment**, not a general-purpose VLA, physical force-closure grasp policy, or real-robot deployment.

**Generation setup (current notebook design):** PyBullet DIRECT, Franka Panda, scripted IK expert waypoints, 240 Hz simulation updates, approximately 8-second episodes, and three cameras (`front`, `overhead`, `side`) producing 192 × 144 observations at 12 FPS (96 frames per episode). The task setup varies initial/goal positions, geometry scale, and selected colors/backgrounds. These are procedural tabletop assets, not a Blender- or GSO-rendered dataset.

### 2.1 Dataset splits

Splits are assigned **before generation** by deterministic task-specific IDs/seeds.

| Split | Per task | Total | Scope of shift |
|---|---:|---:|---|
| Train | 60 | 480 | Training configurations |
| Validation | 10 | 80 | Model selection |
| Test IID | 10 | 80 | New episode seeds within the default distribution |
| Test Compositional | 10 | 80 | Held-out goal-side/location pattern in the current generator |
| Test Visual OOD | 10 | 80 | Held-out color/background palette, not unseen object meshes |
| **Total** | **100** | **800** | |

The **episode** is the splitting and uncertainty-estimation unit. Adjacent frames from one episode must never be assigned to different splits. A `test_compositional` label alone does not establish comprehensive compositional generalization; its precise held-out factor must be documented.

### 2.2 Available modalities and supervision

Each accepted episode is designed to retain source observations, metadata, and downstream labels rather than only precomputed embeddings.

| Stream | Data and provenance |
|---|---|
| RGB / video | Three synchronized camera streams and an expert preview |
| Depth / segmentation / optical flow | Camera-aligned depth, instance masks and estimated flow |
| 3D | Procedural mesh reference, depth-derived point samples, object poses, camera calibration |
| Spoken instruction | Synthesized WAV with instruction transcript; episode-level task condition |
| Environmental audio | Synthetic event/impact audio aligned to recorded events |
| Time series | Object and EE motion, robot joints and velocities |
| Force / contact | Simulation-recorded contacts and derived force signals, with source metadata |
| Tactile | Heuristic dual-finger pressure proxy derived from interaction signals |
| Robot proprioception | Joint configuration, velocities, gripper state and current EE pose |
| EE supervision | Expert commanded target, commanded delta, gripper command, and observed resulting state |
| Task/QA | Task goal, phases, episode outcomes, canonical questions, gold answers and supporting evidence |
| Replay / reproducibility | Scenario parameters, random seed, asset references, version metadata and per-file checksums |

**Important:** synthetic impact sounds and tactile-pressure proxies are not recordings from physical microphones/tactile arrays. Assisted attachment/motion and virtual press/tap triggers are part of the present generator and must be disclosed in any results.

### 2.3 Data integrity and QA generation

The current generator targets **8 canonical, programmatically answered QA items per episode** (up to 6,400 initial pairs across 800 episodes). Optional user-provided API credentials support language paraphrasing; unverified API paraphrases are **not** automatically promoted to gold questions. QA answers should be grounded in saved simulation states/events and include answer type, time range and evidence provenance.

Proposed QA categories for reporting and future **post-processing without rerunning simulation** are: visual recognition, spatial relations, temporal order, contact/force, impact audio, EE/action, outcome, and cross-modal event reasoning. Do not claim that all canonical v1 questions necessarily require multiple modalities; report the categories actually supported by validated labels.

### 2.4 Acceptance requirements

Before accepting an episode, check: successful expert generation under the defined assisted rules; timestamp alignment; camera/EE/world coordinate conventions; observation/action causality; nonempty required files; plausible finite sensor values; QA answer consistency; manifest completeness; and checksums. Keep rejected attempts and their reasons separately. **Notebook code being syntactically valid is not proof that all eight tasks have passed PyBullet runtime validation.** Contributors should run the built-in per-task preflight before full production.

## 3. Proposed model architecture

Every sensory family enters through a **modality-specific encoder branch**; each branch produces compact feature tokens. Some related branches may share a pretrained visual backbone, but their inputs and projected modality identities remain explicit. Projectors map the features to the selected LLM's hidden dimension. A small LLM with LoRA performs cross-modal fusion.

```text
RGB/Video -------- Vision CNN/ViT + temporal module ----┐
Depth/Multiview --- Shared visual backbone / projector -┤
Point Cloud ------- PointNet-style encoder -------------┤
Mesh -------------- Lightweight mesh/graph encoder ----┤
Speech ------------ Pretrained speech encoder ----------┤
Impact Audio ------ Log-mel + CNN ----------------------┤
Motion/Time Series  1D CNN / temporal encoder ----------├─> Modality Projectors
Force/Contact ----- Temporal encoder -------------------┤     + modality/time tokens
Tactile ----------- 2D CNN ----------------------------┤              |
EE/Joint State ---- Small MLP --------------------------┘              v
                                                   Compact LLM + LoRA
                                                      /          \
                                           EE regression head   QA language head
                                           (XYZ + gripper)      (answer tokens)
```

The above **encoder stack is the intended downstream architecture**, not a claim that the Lee/Lazizbek data-generation notebooks already contain trained encoders. Large pretrained encoders may be frozen; lightweight branches, projectors, task heads, and LoRA adapters can be trained. Keep an auditable mapping from each input modality to the emitted feature tokens.

### LLM backbones

1. `Qwen/Qwen2.5-0.5B-Instruct`
2. `meta-llama/Llama-3.2-1B-Instruct`
3. `Qwen/Qwen3.5-2B`
4. `meta-llama/Llama-3.2-3B-Instruct`

For the primary comparison, use **the same external encoder checkpoint(s), modality set, data splits, temporal visibility and token budget** whenever applicable. Train backbone-specific projectors, LoRA adapters and output heads with matched tuning rules. Since Qwen3.5 is natively multimodal while the listed Llama variants are text-only, using native Qwen vision features constitutes a **separately reported extension**, not a fair drop-in replacement for the shared-encoder track.

## 4. Experiments

### E1 — Omni-modal EE-target prediction

**Input:** task instruction plus synchronized observations at or before time `t`. Features may include available visual/3D observations, *past* speech/audio/contact/tactile histories and current robot proprioception.

**Target:** the next **expert-commanded** EE Cartesian target/delta and gripper command. Record and evaluate the next **observed EE pose** separately. Fixed-orientation training should be reported as **XYZ + gripper prediction** rather than learned unrestricted 6DoF control.

**Primary metrics:** teacher-forced absolute EE position MAE in centimeters, relative delta MAE, gripper accuracy/F1, per-task performance, and predicted/expert trajectory visualization. Report IID and both held-out test distributions separately. Never provide future observation channels or expert commands as model inputs.

### E2 — Whole-episode omni-modal question answering

**Input:** the complete *sensor* episode, a question, and optionally the task instruction. Do not feed QA labels, `task.json` gold target values, simulator oracle event logs, or answer-source fields as shortcuts to the model.

**Output:** natural-language or structured answers compared with simulator-grounded gold answers.

**Primary metrics:** per-category and macro-averaged QA accuracy, broken down by task family and test split; use an explicit tolerance for numerical values and event timestamps. Keep the original canonical QA v1 protocol distinct from any subsequently validated QA v2. Retain exact evidence/time annotations for reproducibility.

### E3 — Joint action and QA training

One encoder/projector/LLM+LoRA representation is optimized jointly with separate EE and QA output heads. Compare **Action-only**, **QA-only**, and **Joint Action+QA** training for each backbone. Balance the losses or batch sampling so that many EE timesteps do not drown out the smaller number of episode-level QA items.

Report effects on both E1 and E2, including whether the model's episode-understanding quality correlates with EE prediction quality. A correlation across four backbones is exploratory, not proof of causality.

### E4 — Modality ablations and failure analysis

Compare Full Omni with removal of each meaningful input family: visual, 3D, speech/language, environmental audio, time series, force/contact, tactile, and EE/proprioception. State whether an ablation is evaluated with the original trained model or retrained under matched conditions. Report performance changes **without presuming** that each modality must help. Contact force, audio, and tactile proxies may be highly correlated because they derive from the same scripted interaction events.

### Optional E5 — Model-in-the-loop execution

Model rollout success is **not measured by expert trajectory success flags**. A distinct evaluator must accept each predicted EE action, advance the simulated environment, recompute interactions from the model's executed state, and independently check the task goal. If this evaluator is implemented, report **assisted kinematic task completion** separately from teacher-forced EE prediction. Do not label assisted successes as real-world or unassisted physical manipulation success.

## 5. Fairness, leakage prevention, and reporting

- Publish the dataset and QA generation code versions, encoder checkpoints, modality token counts, LoRA configuration, training seeds and hardware.
- Keep all training/test episodes disjoint, including derived paraphrases and repeated views of one episode.
- **EE visibility:** `(sensor history up to t, instruction) -> expert EE command at t` (or a documented fixed next-step offset).
- **QA visibility:** `(sensor episode 0:T, question) -> verified answer`; labels and oracle simulator metadata are for grading, not model input.
- Do not use the generator's waypoint-phase schedule or future script clock as a privileged control feature unless a privileged experiment is explicitly and separately labeled.
- Use multiple training seeds if practical and calculate uncertainty at the episode level.
- Clearly separate expert-generation acceptance, offline prediction error, optional model-driven assisted success and physical manipulation claims.
- Populate metric tables only after real model evaluation; no numerical performance is claimed in this README.

## 6. Execution roadmap

1. Run the four-task Colab preflight for each owner; verify all modalities, output shapes, action alignment and QA evidence.
2. Generate and save up to 400 accepted episodes per owner to their respective Google Drives, with resumable progress and documented failed attempts.
3. Merge the 800 target episodes under a versioned manifest; verify hashes, counts and split integrity; freeze the dataset snapshot.
4. Build and validate each modality encoder branch and the shared projected-token interface.
5. Fine-tune the four LLM backbones for E1 and E2 separately.
6. Run the joint optimization E3 and modality ablations E4.
7. Optionally implement genuine model-action-driven assisted rollouts (E5).
8. Publish the EE metrics, QA breakdowns, ablation results, representative failures and reproducible training configuration.
